2. What EnerGym Does

EnerGym is a multi-branch gym management SaaS — the operating system for a gym chain. It replaces the tangle of Excel, WhatsApp, and paper that most mid-size gym operators in Vietnam still run on.

The platform covers the full operator workflow in one place:

  • Booking engine — members book classes on a live calendar; staff see rosters and capacity in real time
  • Contract & payment flow — staff draft contracts, apply promotions, activate with one click; invoices and payment links (VNPay, VietQR) are generated automatically
  • Lead CRM — sales pipeline from first contact to signed contract, with CSV import and staff assignment
  • Payroll & commission — automated salary calculation per formula, PT commission tied directly to activated contracts
  • Revenue dashboard — real-time revenue, conversion rate, check-in traffic, and PT performance across branches
  • AI revenue assistant — operators and staff query their own data in plain Vietnamese: "Who are my top leads this week?" or "What's branch Q1's revenue this month?" The AI answers using live data, scoped to what that role is allowed to see

Seven roles access the system — Super Admin, Gym Owner, Branch Admin, Staff (Sales), Personal Trainer, Receptionist, and Member — each with a tailored portal and permission scope.

3. Why I Built It / The Story Behind EnerGym

I chose this project because it allowed me to build more than just software features. It required me to understand business workflows, make architectural decisions, balance development priorities, and integrate AI into a practical product. My goal was not only to complete a graduation project, but also to gain experience building software that solves real operational needs.

The context: mid-size gym chains in Vietnam typically manage memberships in Excel, share contract drafts over Zalo, and calculate staff commissions manually at month end. Revenue data is siloed across branches. A manager overseeing four locations can't answer "what's our total revenue this week?" in under five minutes.

We designed EnerGym to change that — one platform covering the full operator workflow, from the first sales lead to the last payroll record, with an AI assistant that answers operational questions in plain Vietnamese without requiring SQL or spreadsheets.

4. How It Helps

For operators (Branch Admin / Gym Owner / Super Admin):

  • Revenue and KPIs visible in one dashboard — no spreadsheet reconciliation at month end
  • Contract activation triggers invoice generation and commission record automatically — staff can't forget a step
  • The AI assistant answers operational questions in seconds that previously required pulling someone off the floor to check a spreadsheet

For sales staff:

  • Full CRM pipeline — track every lead from cold to signed without switching tools
  • Draft a contract, apply promotions, and send a VNPay payment link in under two minutes
  • Commission is calculated and visible automatically — no disputes at month end

For receptionists:

  • Quick registration for walk-in members (profile setup, package selection, and instant invoicing)
  • Lookup class bookings, check-in history, and member attendance status on front-desk queries

For PTs:

  • Teaching schedule, member rosters, and payroll in one place
  • Commission from member contracts is tracked per contract, not per month-end approximation

For members:

  • Book classes, view their membership, track attendance, and chat with an AI fitness coach — all without calling the front desk

5. Decisions That Were Mine to Make — and the Tradeoffs

① Build the VNPay integration from scratch, not around a wrapper

There's no official VNPay SDK that I'd trust in production. I read the spec and implemented the full flow myself: HMAC-SHA512 signing with params sorted by ASCII key order, IPN webhook verification, idempotency logic to replace stale pending payments instead of creating duplicates, and the exact URI-encoding format VNPay requires (a mismatch here silently corrupts the signature).

Tradeoff: It was slower upfront. But I owned the entire payment layer — no black-box library that breaks on a VNPay API version bump and takes a maintainer's PR cycle to fix. For a revenue-critical path, that control was worth it.

② Microsoft Semantic Kernel over raw OpenAI API calls

I could have hit the OpenAI endpoint directly and parsed the JSON. Instead I used Microsoft Semantic Kernel, which gave me a proper tool-calling abstraction and a one-config swap between OpenAI and Ollama (a local LLM). The AI module ended up with 20+ tools, a function invocation filter for audit logging, and an RBAC layer that resolves which tools each user role can call at runtime.

Tradeoff: Heavier dependency and a steeper learning curve. SK 1.30 had breaking changes from earlier versions and sparse documentation for some patterns. But the abstraction paid off — swapping the LLM provider is now a config change, not a code rewrite. For operators who can't send employee data to US servers, that matters.

③ Role-scoped AI tools instead of one generic assistant

The easier path was one chatbot that could answer anything. I built 20+ tools grouped by domain (Revenue, Payroll, Leads, Booking, Attendance, Contract…) and filtered them per role at runtime via an AIToolRegistry. A branch manager asking "today's revenue?" gets branch-scoped numbers. The chain owner gets system-wide. A PT asking the same question gets their personal earnings. The LLM picks the right tool — my job was designing the permission layer and the context resolution that resolves userId → role → branchId before any tool runs.

Tradeoff: Far more engineering than a generic chatbot. But a generic assistant that shows a branch manager another branch's revenue is a product liability, not a feature. Trust in the data is the product.

④ Monolith with clean layered architecture over microservices

Two developers. Four months. A thesis deadline. Microservices would have added network contracts, service discovery, and distributed debugging overhead before we'd shipped a single feature. I chose a layered monolith — Controllers → Interfaces → Services → EF Core — with clear boundaries that don't bleed. Each service owns its domain; none import each other directly.

Tradeoff: Harder to scale individual components independently. But premature extraction is a known failure mode for small teams. The architecture is designed to be extracted later — domain boundaries are already drawn.

⑤ Code-First database design over DB-First

I designed the 49-table schema entirely in C# models and let EF Core generate migrations. This kept the schema version-controlled alongside the code, made rollbacks predictable, and enforced domain modeling discipline — every relationship is explicit in code before it exists in the database.

Tradeoff: EF Core migrations accumulate technical debt (36 migrations over the project lifespan), and complex queries sometimes need raw SQL to avoid N+1 issues. The payoff was a schema that evolved safely with the product without manual ALTER TABLE scripts.
